## 2. 分层职责（面试必答：为什么分层）

| 层 | 职责 | 内容 | 写入方式 |
|---|---|---|---|
| ODS | 原始数据落地，不加工 | 业务表镜像 + 行为日志原始 JSON | DataX / Flume |
| DIM | 维度标准化、去重、补全 | 用户（拉链表）、商品、分类、地区、时间 | Spark SQL |
| DWD | 数据清洗 + 明细事实 | 交易明细、流量明细，列裁剪、去重、JSON 拉平 | Spark SQL |
| DWS | 按主题汇总成宽表 | 用户/商品/地区/时间四主题，减轻 ADS 重复计算 | Spark SQL |
| ADS | 输出业务指标 | GMV、UV、留存、复购等，导出 MySQL 供可视化 | Spark SQL + DataX |

**分层的目的**（面试要能说清三条）：
1. 空间换时间：预聚合，避免每次查询全量扫描；
2. 职责解耦：每个环节只做一件事，便于定位问题、数据可追溯；
3. 统一口径：指标在 DWS/ADS 只算一遍，全公司（项目内所有报表）口径一致。

## 3. 命名规范

- 库：`gmall_ods` / `gmall_dim` / `gmall_dwd` / `gmall_dws` / `gmall_ads`（清晰分层，面试好讲）
- 表：`ods_` / `dim_` / `dwd_` / `dws_` / `ads_` 前缀 + 业务域 + 粒度，如 `dws_sku_stats_day`（日粒度商品主题）
- 分区：按天分区 `dt=yyyy-MM-dd`；日志明细表可再加 `hr` 小时分区
- 字段：snake_case；金额 `decimal(16,2)`；时间 `timestamp`；所有表保留 `dt` 分区字段
- 存储：Hive 外部表 + ORC + Snappy（列式存储，压缩比高）

## 4. 维度建模设计

**模型**：星型模型 —— 事实表（明细/汇总）在中间，维度表（DIM）围绕四周，通过外键关联。

**事实表两类**：
- 事务型事实表：一笔业务一行（订单明细、支付流水）—— 下单、支付属于这类；
- 周期型快照事实表：按时间周期统计状态（如每日订单状态快照）。

**缓慢变化维（SCD）处理**：
- 用户地址、等级等经常变的维度 → **拉链表**（Type 2：保留历史版本，加 `start_date`/`end_date` 区间）
- 商品名称等几乎不变的属性 → 覆盖写（Type 1）

**拉链表（面试必考）**：
- 原理：每日用「全量初始化 + 增量更新」把变化行追加进历史链，查询时用 `dt <= end_date` 过滤当前版本
- 为什么不用每日全量快照：数据量 3 个月后膨胀 90 倍，拉链只存变化行
- 实现：`DIM 初始化`（历史全量打上区间）→ `DIM 每日更新`（昨日全量 LEFT JOIN 拉链表，新增/变化行插入，并关闭旧版本）

## 5. 指标口径表（面试必答：口径怎么定义）

> 口径不统一是数仓最大的坑，面试官必问。这里的定义就是本项目唯一口径，写进文档防止自己前后矛盾。

| 指标 | 口径定义 | 归属层 |
|---|---|---|
| GMV | 支付成功的订单金额合计，按**支付时间**统计 | ADS 交易 |
| 订单数 | 下单成功的订单数，按**下单时间**统计 | ADS 交易 |
| 客单价 | GMV ÷ 支付订单数 | ADS 交易 |
| 退款率 | 退款金额 ÷ GMV | ADS 交易 |
| PV / UV | 页面浏览数 / 按 user_id 去重的独立访客数 | ADS 流量 |
| 转化率 | 下单用户数 ÷ 浏览用户数（漏斗：浏览→加购→下单→支付） | ADS 流量 |
| 次日留存率 | 某日新增用户中，次日仍有活跃行为的占比 | ADS 用户 |
| 复购率 | 统计周期内购买 ≥2 次的用户数 ÷ 购买用户数 | ADS 用户 |

## 6. 调度依赖

```
ODS(前日 23:00 采集完成)
   │
   ▼
DIM → DWD(清洗) → DWS(汇总) → ADS(指标) → DataX 导出 MySQL(次日 02:00 前完成)
   ▲
quality 检查节点嵌在每一层之后，失败则阻断下游
```

Airflow DAG 实现，失败自动重试；详情见 [scheduler/](../scheduler/README.md)。
